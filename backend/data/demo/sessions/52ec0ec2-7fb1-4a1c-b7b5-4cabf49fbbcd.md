7.12.4　命中计数和使用限制
RFC 2227，“HTTP 的简单命中计数和使用限制”中定义了一种简单得多的方案。这
个协议向 HTTP 中添加了一个称为Meter 的首部，这个首部会周期性地将对特定
URL 的命中次数回送给服务器。通过这种方式，服务器可以从缓存周期性地获取对
已缓存文档命中次数的更新。
而且，服务器还能控制在缓存必须向服务器汇报之前，其中的文档还可以使用多少
次，或者为缓存文档设置一个时钟超时值。这种控制方式被称为使用限制；通过这
种方式，服务器可以对缓存向原始服务器汇报之前，已缓存资源的使用次数进行 
控制。

HTTP 定义了一组被称为安全方法的方法。GET 方法和 HEAD 方法都被认为是安全

这种情况下，为购买行为支付信用卡就是所执行的动作。
安全方法并不一定是什么动作都不执行的（实际上，这是由 Web 开发者决定的）。
使用安全方法的目的就是当使用可能引发某一动作的不安全方法时，允许 HTTP 应
用程序开发者通知用户。在 Joe 的五金商店的例子中，你的 Web 浏览器可能会弹出
一条警告消息，说明你正在用不安全的方法发起请求，这样可能会在服务器上引发

## HTTP 请求格式详解 📖

### 一、整体结构

一个 HTTP 请求报文由三大部分组成：

```
┌──────────────────────────────────┐
│ 1. 起始行（请求行）               │
├──────────────────────────────────┤
│ 2. 首部（Headers）               │
├──────────────────────────────────┤
│ 3. 实体主体（Entity Body）        │
└──────────────────────────────────┘
```

标准格式如下：

```
<method> <request-URL> <version>
<headers>
空白行（CRLF）
<entity-body>
```

---

### 二、第一部分：请求行（Start Line / Request Line）

请求行是请求报文的第一行，包含三个字段：

```
GET /specials/saw-blade.gif HTTP/1.1
│     │                        │
│     │                        └─ HTTP 版本
│     └─ 请求 URL（资源路径）
└─ 方法（Method）
```

| 组件 | 说明 | 示例 |
|------|------|------|
| **方法** | 客户端想让服务器执行的动作 | `GET`、`POST`、`PUT`、`DELETE` |
| **请求 URL** | 所请求资源的路径 | `/index.html`、`/api/users` |
| **版本** | HTTP 协议版本 | `HTTP/1.0`、`HTTP/1.1`、`HTTP/2.0` |

> 如果你直接与服务器通信，URL 的路径组件使用绝对路径即可（如 `/specials/...`）；如果要经过代理，可能需要完整 URL。

---

### 三、第二部分：请求首部（Request Headers）

首部行跟在请求行之后，格式为 `名称: 值`，每条占一行。常见请求首部包括：

| 首部 | 作用 | 示例 |
|------|------|------|
| `Host` | 指定目标主机（HTTP/1.1 必须） | `Host: www.joes-hardware.com` |
| `Accept` | 告诉服务器客户端能处理的内容类型 | `Accept: text/html, image/gif` |
| `Content-Type` | 请求主体的数据类型（POST/PUT 用） | `Content-Type: text/plain` |
| `Content-Length` | 请求主体的字节长度 | `Content-Length: 34` |
| `User-Agent` | 客户端应用信息 | `User-Agent: Mozilla/5.0` |
| `Connection` | 连接管理选项 | `Connection: Keep-Alive` |
| `Cache-Control` | 缓存指令 | `Cache-Control: no-cache` |

**请求首部的结束**由一个**空行**（CRLF，即 `\r\n\r\n`）标记，这个空行之后就是主体部分。

---

### 四、第三部分：实体主体（Entity Body）

不是所有请求都有主体。主体承载要发送给服务器的数据。

| 方法 | 是否有主体 |
|------|-----------|
| `GET` | ❌ 无 |
| `HEAD` | ❌ 无 |
| `DELETE` | ❌ 无（通常） |
| `POST` | ✅ 有（如表单数据、JSON） |
| `PUT` | ✅ 有（如文件内容） |
| `TRACE` | ❌ 不能有 |
| `OPTIONS` | ❌ 无（通常） |

---

### 五、并发一个完整的请求示例

```
POST /api/login HTTP/1.1
Host: www.example.com
Accept: application/json
Content-Type: application/json
Content-Length: 44
Connection: Keep-Alive
                          ← 空行！
{"username": "alice", "password": "123456"}
```

逐行解读：
1. **请求行**：用 `POST` 方法访问 `/api/login`，协议 `HTTP/1.1`
2. **Host**：目标主机 `www.example.com`
3. **Accept**：希望收到 JSON 格式响应
4. **Content-Type**：我发给你的数据是 JSON
5. **Content-Length**：主体有 44 字节
6. **空行**：首部结束信号
7. **实体主体**：JSON 数据

---

### 六、常见的 HTTP 方法一览

| 方法 | 描述 | 是否有主体 | 安全性 |
|------|------|-----------|--------|
| **GET** | 从服务器获取资源 | ❌ | ✅ 安全 |
| **HEAD** | 只获取首部（没有主体） | ❌ | ✅ 安全 |
| **POST** | 向服务器提交数据 | ✅ | ❌ 不安全 |
| **PUT** | 将请求主体存储到服务器 | ✅ | ❌ 不安全 |
| **DELETE** | 删除指定资源 | ❌（通常） | ❌ 不安全 |
| **TRACE** | 追踪经代理的报文 | ❌ | ✅ 安全 |
| **OPTIONS** | 查询服务器支持的方法 | ❌（通常） | ✅ 安全 |

> **安全方法**（GET、HEAD、OPTIONS、TRACE）不会在服务器上产生副作用，也就是说它们只是获取信息，不应该改变服务器状态。

---

### 七、一句话总结

> HTTP 请求 = **请求行**（方法 + URL + 版本） + **首部**（Host、Content-Type 等元信息） + 空行 + **可选主体**（POST/PUT 时的数据）。
